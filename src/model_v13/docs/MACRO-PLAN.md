### Bug #2 — CRITICAL: forward_pass uses h_cache as both the running h state AND as h_cache for backward

**File:** `src/train.c`, lines 36-46
**Code:**
```c
memset(h_cache, 0, (size_t)seq_len * ds * sizeof(float));

ssm_scan_forward(
    L->A, NULL, L->B, 0, L->C,
    x_proj,
    h_cache,    // <-- passed as 'h' (the running SSM state — should be ONE d_state vector)
    y_ssm,
    h_cache,    // <-- also passed as h_cache (the per-timestep snapshot — seq_len * d_state)
    ...
```
**Problem:** `ssm_scan_forward` expects its `h` argument to be a single `[d_state]` vector (updated in-place at each timestep). It expects `h_cache` to be a `[seq_len * d_state]` buffer where it saves snapshots. By passing the same pointer for both:
- At t=0: `h[0..d_state]` is correct, then saved to `h_cache[0..d_state]` = same location. OK.
- At t=1: ssm_scan reads `h` from `h_cache[0..d_state]` (now correctly the t=0 state). But it also saves snapshot at `h_cache[d_state..2*d_state]`. So far still works.
- But: the ssm_scan signature contract says `h` is the initial state (before t=0), NOT a sliding window. The forward loop in ssm_scan.c line 109+ reads from `h` directly (not indexed by t), then writes `h_cache[t * d_state + i]`. So the running state IS `h` (one vector), and `h_cache` is the output snapshot array. When both point to the same buffer, `h` is aliased to h_cache[0..d_state]. After t=0 finishes, `h` has been written in-place — so h_cache[0] holds the t=0 state, and `h` points to h_cache[0] which is the t=0 state, which is also the input to t=1. That is actually accidentally correct.

Wait — this is an alias issue but the ACTUAL bug is: after the layer-0 forward, the NEXT layer needs the h vector to be ZEROED (fresh initial state). The `memset(h_cache, 0, ...)` at the start of each layer zeroes the h_cache buffer, which also zeroes the initial h (since they alias). So h is correctly zeroed before each layer. The alias is dangerous but accidentally works when h is the first d_state elements of h_cache.

HOWEVER: the REAL bug is that this alias means if the scan writes anything to h_cache[t * d_state] for t > 0, and h is a pointer to h_cache[0], then h does NOT get corrupted because the scan only reads h once per step and writes h back before reading the next snapshot location. The scan is:
```
h[i] = A[i]*h[i] + B[i]*x[i]   // h updated in place (h points to h_cache[0])
memcpy(h_cache + t*d_state, h, ...)  // saves current h to h_cache[t]
```
At t=0: h_cache[0] = updated h = h_cache[0] (no-op memcpy, since src==dst). At t=1: reads h (= h_cache[0] = t=0 state), updates it, saves to h_cache[1*d_state]. Correct but wasteful (the memcpy at t=0 is a self-copy).

**The real problem with this alias is the backward pass** — see Bug #3.

**Fix:** Allocate a separate `float h_init[V12_D_STATE]` as the running state per layer. Keep `h_cache` as the snapshot buffer. This is a clean 2-line change.

### Bug #3 — CRITICAL: backward_pass uses wrong buffer for d_h accumulation

**File:** `src/train.c`, lines 68-69 and 124-143
**Code:**
```c
float *d_h = c->d_residual;        // line 69: d_h points to d_residual[0..seq*d]
memset(d_h, 0, seq_len * d * ...); // only zeroes the first seq_len*d floats
```
Then for each layer backward:
```c
float *h_input = c->residual;   // line 125: uses residual (forward activations) as input
```
**Problems:**
1. `d_h` is initialised as a pointer to `c->d_residual` which has shape `[n_layers * seq_len * d_model]`. But the code only zeroes and uses `seq_len * d_model` elements. When we process layer k, we should be accumulating gradients into the layer-k slice. The current code accumulates all layers' d_h into the same `[0..seq_len*d_model]` prefix, so each layer OVERWRITES the d_h from the previous layer. This means only layer 0's gradient w.r.t. the residual stream is ever used by the embedding.

2. `h_input = c->residual` (line 125) is the SAME pointer used as the residual stream across all layers. After layer 0's forward pass, `h` (which is `c->residual`) contains the final-layer output (since the forward loop modifies it in-place). The backward incorrectly uses the FINAL-layer activations as the input to every layer's W_in gradient, instead of the per-layer saved input.

3. The W_in backward (line 128-131):
```c
L->dw_in[i * d + j] += d_x_proj[t * ds + i] * h_input[t * d + j];
```
This computes `dL/dW_in[i,j] = sum_t d_x_proj[t,i] * input[t,j]`. The `h_input` should be the LAYER INPUT (residual stream BEFORE layer k), but `c->residual` holds the FINAL residual after all layers. The gradient is wrong for every layer except layer 0.

**Fix:** The forward pass must save per-layer residual inputs into `c->residual[k * seq_len * d_model + ...]`. The forward_pass as currently written modifies the residual in-place (one shared buffer) and never saves layer inputs. This is the root cause.

**Specific fixes needed in forward_pass:**
- Change `float *h = c->residual` (single shared buffer) to use c->residual as a layer-indexed buffer
- Before each layer k: copy current residual into `c->residual[k * seq_len * d_model]`
- This allows backward to read the correct per-layer input

**Lines affected:** ~20 lines in forward_pass, ~15 lines in backward_pass.

### Bug #4 — OOM CAUSE: lm_head CSR allocation at model_alloc is huge

**File:** `src/core/model.c`, lines 332-347 (model_rebuild_lm_head_csr)
**Problem:** The lm_head CSR is built with `rows = V12_VOCAB_SIZE = 32064`, `cols = V12_D_MODEL = 1024`. Even with ~33% nonzero ternary weights (at step 0, shadow_lm_head is initialized to small values ~0.1, so most sampled weights will be 0 — but the allocation is still:
- `int8_t *buf = malloc(n)` where `n = 32064 * 1024 = 32.8 MB` — this is the temporary int8 buffer.
- `pos_indices + neg_indices` at ~1/3 density: ~11 million int32 entries = 44 MB.
- `row_ptr_pos + row_ptr_neg`: `2 * (32064 + 1) * 4 = 256 KB`.
- `n_pos + n_neg`: `2 * 32064 * 4 = 256 KB`.

At step 0, the shadow logits are sampled from ~N(0, 0.1), so |s| < 0.5 for almost all entries, and `sample_ternary_from_logit` returns 0 for those. Effective nonzero ~0%. But `ternary_csr_init` still allocates `total_pos + total_neg` sized index arrays. If all weights happen to be 0, it allocates NULL (see lines 128-145 of ternary_matmul.c). So actual CSR at step 0 is tiny.

The OOM must be caused by the FORWARD PASS lm_head:
```c
ternary_matvec(&m->csr_lm_head, h + t * d, c->logits + t * V12_VOCAB_SIZE);
```
At step 0 with all-zero CSR, this produces all-zero logits. CE loss of log(32064) ≈ 10.37 nats. That is correct. But the CSR forward gives ALL ZEROS in logits, so softmax is uniform, and d_logits is extremely small (1/32064 per position). Gradients will be tiny.

**The real OOM cause (more likely):** The backward lm_head dense loop (lines 73-86 of train.c):
```c
for (int t = 0; t < seq_len; t++) {
    for (int j = 0; j < d; j++) {         // 1024
        float acc = 0.0f;
        for (int v = 0; v < V; v++) {      // 32064
            acc += m->sampled_lm_head[v * d + j] * c->d_logits[t * V + v];
        }
        d_h[t * d + j] = acc;
    }
    for (int v = 0; v < V; v++) {          // 32064
        for (int j = 0; j < d; j++) {      // 1024
            m->dlm_head[v * d + j] += c->d_logits[t * V + v] * h_final[t * d + j];
        }
    }
}
```
This is `2 * seq_len * V * D = 2 * 512 * 32064 * 1024 = ~33.6 billion float ops per step` in pure scalar triple-nested loops. At ~2 GFLOP/s scalar C, this is **~16 seconds per step** for just the lm_head backward. This is WHERE the 10s/step comes from.

Additionally, `sampled_lm_head` at step 0 is all zeros (since shadow logits are ~0.1 and most sample to 0), so `d_h` from lm_head is zero, and `dlm_head` is non-zero (d_logits * h_final). This means the only gradient flowing into the model through lm_head backward is dlm_head, and d_h is zero. So NO gradient reaches the SSM layers through lm_head. Only the W_in/W_out gradients accumulate, and even those use the wrong residual input (Bug #3).

**Fix:** See Phase 1 item 3 below.

### Bug #5 — MINOR: train_step passes wrong targets offset to CE functions

**File:** `src/train.c`, lines 161-163
```c
float loss = compute_ce_loss(c, c->logits, tokens + 1, V12_VOCAB_SIZE, seq_len);
compute_ce_backward(c, c->logits, tokens + 1, V12_VOCAB_SIZE, seq_len);
```
The `compute_ce_loss` function internally accesses `targets[t + 1]` (see loss.c line 95). If the caller already passes `tokens + 1`, then the effective target is `tokens[t + 2]`, predicting TWO tokens ahead.

**Fix:** Pass `tokens` (not `tokens + 1`) to both loss functions. The loss functions handle the +1 offset internally.

### Bug #6 — MINOR: mvue_sample_weights writes sampled value into shadow_w_conv instead of dedicated sampled_w_conv

**File:** `src/core/optimizer.c`, lines 32-38
```c
for (int i = 0; i < n_conv; i++) {
    float s = layer->shadow_w_conv[i];
    float u = uniform01(rng_state);
    float w = sample_ternary_from_logit(s, u);
    layer->shadow_w_conv[i] = w;   // BUG: should write to a sampled_w_conv buffer
}
```
The conv weights have no dedicated `sampled_w_conv` float buffer in the current alloc (though `shadow_w_conv` is allocated). This overwrites the shadow logits with the sampled value, destroying the continuous logit information used for the MVUE gradient update. Since conv is not yet used in the forward pass (train.c bypasses it), this is not currently a training correctness issue — but it will corrupt state when conv is added.
**Fix:** Either add `sampled_w_conv` field to SSMLayer, or (for MVP) remove the conv sampling from mvue_sample_weights entirely and add it back when conv1d is implemented.

### Bug #7 — PERFORMANCE: D4 sign consistency filter blocks ALL updates for 5 steps

**File:** `src/core/optimizer.c`, lines 74-84
**Problem:** The D4 filter requires 5 CONSECUTIVE gradient signs to agree before updating. At step 0, sign_hist_w_in is all zeros (calloc). The current gradient sign may be +1 or -1. Comparison with the zeroed history will always fail (sign_cur != 0 != sign in hist). Result: NO weight updates at all for the first 5 steps. This is by design but means loss is completely flat for steps 0-4.

For MVP/debugging this is fine, but it means convergence will be slow early. For Phase 1 testing, disable D4 temporarily.

### Phase 2 — Fix Performance (Speed)

Goal: < 1 second per step. Current: ~10s/step due to lm_head backward.

**2.1 — Replace dense lm_head backward with transposed CSR matvec**
- File: `src/train.c`, backward_pass, lines 73-86
- Current: Triple-nested scalar loop. `512 * 32064 * 1024 = 33 billion ops`.
- Fix: The lm_head backward is two operations:
  - `d_h[t] = W_lm^T @ d_logits[t]` — this is a transposed CSR matvec. Since W_lm is ternary {-1,0,+1}, the transposed matmul is: for each nonzero entry (row=v, col=j) with weight w, add `w * d_logits[t*V + v]` to `d_h[t*d + j]`. This is exactly what ternary_matvec does on the TRANSPOSE CSR (swap pos/neg index roles).
  - `dlm_head[v,j] += d_logits[t,v] * h[t,j]` — this is a dense outer product. It CANNOT be sparsified because d_logits is dense (softmax output). However, we can speed it up significantly by:
    a. Only updating dlm_head where |d_logits[t,v]| is above a threshold (most softmax values are near 1/32064 ≈ 3e-5; only the target token and top-K have meaningful gradients).
    b. For MVP: reorder the loop for better cache behavior (v outer, j inner, prefetch h[t,j]).
- For d_h via transposed CSR: add `ternary_matvec_transpose` function that walks the CSR rows but accumulates into columns of the output.
- **Fastest MVP fix**: reduce V12_VOCAB_SIZE in types.h from 32064 to 4096 for initial testing. Reduces the bottleneck by 8x. Use a correspondingly smaller dataset (byte-level or small BPE tokenizer). This requires no code changes, only a constant change and dataset re-tokenization.
- **Better fix**: implement `ternary_matvec_T` (transposed matvec using CSR pos/neg indices) and use it for the d_h computation. For dlm_head, add a sparse-threshold outer product that only updates entries where |d_logits[t,v]| > 1e-4.
- Estimated speedup: 10-50x for lm_head backward.
- Lines: ~30 new lines in ternary_matmul.c, ~15 changed in backward_pass.
- Files: `src/core/ternary_matmul.h`, `src/core/ternary_matmul.c`, `src/train.c`.
- Dependencies: 1.x all fixed.

## Part 8 — Answers to the Specific Questions

**Q1: Minimum Viable Product?**
Fix 7 bugs (Phase 1.1 through 1.7) and add Makefile. Total: ~80 lines changed across 3 files plus 1 file deleted. No new features needed. The SSM layers are complete and correct; only train.c has the integration errors.

**Q2: What's causing 10s/step?**
Confirmed: it is the lm_head backward dense triple-nested loop in backward_pass (lines 73-86 of train.c). `512 * 32064 * 1024 = 33 billion float operations in pure scalar C`. The forward lm_head (32064 CSR matvecs per sequence) is much faster because CSR exploits sparsity. The backward is dense because d_logits is dense (softmax output).

Fastest fixes in priority order:
1. Reduce VOCAB_SIZE to 4096 for development (8x speedup, 0 code changes).
2. Implement transposed-CSR matvec for `d_h = W_lm^T @ d_logits[t]` (sparsity exploited).
3. Sparse-threshold outer product for `dlm_head += d_logits[t] (x) h[t]` (only update high-gradient entries).

**Q3: Are gradients correct?**
No. Three correctness bugs:
- Bug #2: h/h_cache alias (benign at runtime but conceptually wrong).
- Bug #3: backward uses wrong residual input (all layers compute wrong dw_in).
- Bug #5: target offset double-shifted (predicting 2 tokens ahead instead of 1).

**Q4: Memory usage — why OOM?**
The allocation is ~737 MB, not 1.4 GB. This should not OOM 32 GB. The OOM is likely a transient peak during lm_head CSR init (temporary 32 MB int8 buffer in model_rebuild_lm_head_csr) plus the 33 billion op backward loop that may trigger page faults across all touched memory in a single hot loop, causing the OS to kill the process for excessive memory pressure — not true OOM but virtual address pressure. Alternatively, the OOM may be from an earlier version. With the current code, it should run without OOM.

**Q5: Correct Makefile?**
See Part 4 above. Key points: include all 7 .c files, do NOT include gp_kl_stub.c, use `-I src/` for includes, `-lm` for math, `-march=native` for AVX2.

**Q6: What is NOT needed for MVP?**
See Part 5 above. conv1d, layer norm, checkpoint, MTP, W_pred, GP-KL wiring, cospec, INT2 repack, D4 filter — all can wait.
